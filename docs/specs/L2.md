# L2 - Detailed Requirements

Each L2 traces to exactly one L1 in [L1.md](L1.md). Acceptance criteria use Given/When/Then so they translate directly into acceptance tests. Every acceptance test file must start with a comment naming the L2 requirement(s) it covers, for example:

```typescript
// Acceptance Test
// Traces to: L2-013
// Description: Verify the API rejects a listing that is not for girls
```

```csharp
// Acceptance Test
// Traces to: L2-029
// Description: Verify only one of two concurrent purchases of the same listing succeeds
```

Unless stated otherwise, amounts are in US dollars, times are UTC, and "member" means a signed-in account holder.

---

## L2-001: Registration
**Traces to:** L1-001

A visitor shall be able to register with a display name, an email address and a password. The display name shall be 3 to 30 characters of letters, digits, underscores or hyphens and unique ignoring case. The email address shall be a valid address unique ignoring case. The password shall be 12 to 128 characters and shall not appear in a list of known breached passwords. The visitor shall confirm they are 18 or older and accept the terms of service.

**Acceptance Criteria:**
1. Given a visitor on the registration page, when they submit a unique display name, a unique valid email, a 12-character password not on the breached list, the age confirmation and terms acceptance, then an unverified account is created and a verification email is sent.
2. Given an existing account with email `Sam@Example.com`, when a visitor registers with `sam@example.com`, then registration is rejected with the message "An account with this email already exists" and no account is created.
3. Given an existing display name `tutu_tessa`, when a visitor registers with `TUTU_TESSA`, then registration is rejected with a "display name is taken" error.
4. Given a password of 11 characters, when the visitor submits the form, then registration is rejected with "Password must be at least 12 characters".
5. Given a password that appears in the breached password list, when the visitor submits the form, then registration is rejected with "This password has appeared in a data breach. Choose another."
6. Given the age confirmation or terms checkbox is not ticked, when the visitor submits the form, then registration is rejected and the unticked field is marked as required.
7. Given a display name of 2 or 31 characters, or one containing a space, when the visitor submits the form, then registration is rejected with a display name format error.

## L2-002: Email verification
**Traces to:** L1-001

A new account shall be verified by a single-use link emailed to the member. The link shall expire 24 hours after it is sent. Unverified members shall be able to browse but not list or buy.

**Acceptance Criteria:**
1. Given an unverified account, when the member opens the verification link within 24 hours, then the account is marked verified and the member sees a confirmation page.
2. Given a verification link older than 24 hours, when the member opens it, then verification fails with "This link has expired" and an option to resend.
3. Given a verification link that has already been used, when it is opened again, then verification fails and the account state does not change.
4. Given an unverified member, when they try to create a listing or start checkout, then the action is refused with HTTP 403 and the UI prompts them to verify their email.
5. Given an unverified member, when they request a new verification email, then a new link is sent and every earlier link for that account stops working.
6. Given 3 verification links were sent to a member in the last hour (the registration email counts as the first), when they request another, then the request is refused with HTTP 429 and a `Retry-After` header.
7. Given an email that has no unverified account, when a new link is requested for it, then the API answers as it would for an unverified account and no email is sent, so the request reveals nothing.

## L2-003: Buy and sell with one account
**Traces to:** L1-001

Every verified member shall be able to both buy and sell. There shall be no seller application, approval or separate seller account.

**Acceptance Criteria:**
1. Given a newly verified member, when they open "Sell an item", then the listing form opens without any approval step.
2. Given a newly verified member, when they open an active listing owned by another member, then the "Buy now" action is available.

## L2-004: Profile management
**Traces to:** L1-001

A member shall be able to edit their display name, bio (up to 500 characters), avatar image and public location. The public location shall be limited to a city and state or region. The display name rules of L2-001 apply to changes.

**Acceptance Criteria:**
1. Given a signed-in member, when they save a bio of 500 characters, then the bio is saved and shown on their public profile.
2. Given a signed-in member, when they save a bio of 501 characters, then the save is rejected with a length error.
3. Given a signed-in member, when they change their display name to one already in use ignoring case, then the save is rejected with "display name is taken".
4. Given a signed-in member, when they upload an avatar, then the image is validated and processed under the same rules as listing photos (L2-017) and shown on their profile.
5. Given a signed-in member, when they set a public location, then only the city and state or region are stored for public display and no street address field is offered.

## L2-005: Account closure
**Traces to:** L1-001

A member shall be able to close their account. Closure shall be refused while the member has an order that is not Completed, Cancelled or Refunded. On closure, the member's active and draft listings shall be removed, they shall be signed out everywhere, and their personal data shall be erased within 30 days, except order records the law requires TuTuMuch to keep, which shall be kept in anonymised form.

**Acceptance Criteria:**
1. Given a member with no open orders, when they confirm account closure by re-entering their password, then the account is closed, all sessions are revoked and all their active and draft listings stop appearing in the catalog.
2. Given a member with an order in Paid, Shipped or Delivered status, when they try to close their account, then closure is refused with a message listing the open orders.
3. Given an account closed 30 days ago, when the erasure job has run, then the account's email, display name, bio, avatar, addresses and photos are erased and past orders show the member as "Former member".
4. Given a closed account, when someone tries to sign in with its credentials, then sign-in fails with the same generic error used for wrong credentials.

## L2-006: Sign in
**Traces to:** L1-002

A member shall be able to sign in with their email and password. The error shown for an unknown email and for a wrong password shall be identical.

**Acceptance Criteria:**
1. Given a verified member, when they sign in with the correct email and password, then a session is created and they are returned to the page they came from.
2. Given an unknown email, when someone tries to sign in, then the response is "Email or password is incorrect" with the same status code as a wrong password.
3. Given a wrong password for a known email, when someone tries to sign in, then the response is "Email or password is incorrect".
4. Given the email is entered with different capitalisation from the one registered, when the member signs in with the correct password, then sign-in succeeds.

## L2-007: Brute-force protection
**Traces to:** L1-002

After 5 failed sign-in attempts for one account within 15 minutes, the account shall be locked for 15 minutes. Sign-in attempts from one IP address shall be limited to 20 per 15 minutes.

**Acceptance Criteria:**
1. Given 5 failed sign-in attempts for an account within 15 minutes, when a sixth attempt is made with the correct password, then sign-in is refused and the member is told to try again later.
2. Given an account locked 15 minutes ago, when the member signs in with the correct password, then sign-in succeeds.
3. Given 20 sign-in attempts from one IP address within 15 minutes, when a 21st attempt is made, then the API returns HTTP 429 with a `Retry-After` header.
4. Given an account is locked, when the lock starts, then the member is sent an email saying their account was temporarily locked.

## L2-008: Session management
**Traces to:** L1-002

Sessions shall use a short-lived access token (15 minutes) and a rotating refresh token (14 days) held in `HttpOnly`, `Secure`, `SameSite=Strict` cookies. Tokens shall never be stored in `localStorage` or `sessionStorage`. Signing out shall revoke the session on the server.

**Acceptance Criteria:**
1. Given a successful sign-in, when the response is inspected, then the session cookies carry the `HttpOnly`, `Secure` and `SameSite=Strict` attributes and no token is written to web storage.
2. Given an access token older than 15 minutes and a valid refresh token, when the app calls the API, then a new access token and a new refresh token are issued and the old refresh token is invalidated.
3. Given a refresh token that has already been used, when it is presented again, then the request is refused and every session in that token family is revoked.
4. Given a member signs out, when the old refresh token is presented, then it is refused with HTTP 401.
5. Given a member with sessions on two devices, when they choose "Sign out everywhere", then both sessions are revoked.
6. Given no activity for 14 days, when the member returns, then they are asked to sign in again.

## L2-009: Password reset
**Traces to:** L1-002

A member shall be able to reset a forgotten password through a single-use emailed link that expires after 1 hour. The response to a reset request shall not reveal whether the email is registered. Resetting the password shall revoke all of the member's sessions.

**Acceptance Criteria:**
1. Given a registered email, when a reset is requested, then the page shows "If an account exists for this email, we've sent a link" and a reset email is sent.
2. Given an unregistered email, when a reset is requested, then the page shows the same message, with the same status code, and no email is sent.
3. Given a reset link opened within 1 hour, when the member sets a new password that meets L2-001 rules, then the password is changed, all existing sessions are revoked, and a confirmation email is sent.
4. Given a reset link older than 1 hour or already used, when it is opened, then the reset is refused with "This link has expired".
5. Given 3 reset requests for one email in the last hour, when a fourth is made, then no further email is sent.

## L2-010: Authorisation
**Traces to:** L1-002

Every API endpoint shall check that the caller is allowed to act on the resource. A member shall only change their own profile and listings, and shall only see orders they are the buyer or seller of. Administrator endpoints shall require the Administrator role. Requests for resources the caller is not allowed to see shall return HTTP 404 so their existence is not revealed.

**Acceptance Criteria:**
1. Given member A and a listing owned by member B, when A sends an update or delete request for that listing, then the API returns HTTP 404 and the listing is unchanged.
2. Given an order between members B and C, when member A requests that order, then the API returns HTTP 404.
3. Given a member without the Administrator role, when they call any administrator endpoint, then the API returns HTTP 403.
4. Given an anonymous visitor, when they call any endpoint that changes data, then the API returns HTTP 401.

## L2-011: Accepted categories and sizes
**Traces to:** L1-003

TuTuMuch shall accept only the categories and sizes in this table. The list is held on the server and served to the client.

| Category | Subcategories | Accepted size |
| --- | --- | --- |
| Clothing | Dresses, Tops, Bottoms, Outerwear, Pajamas, Swimwear | Girls' |
| Shoes | Sneakers, Boots, Sandals, Dress shoes | Girls' |
| Dance | Tutus, Leotards, Dance shoes, Dance bags | Girls' |
| Sports | Soccer, Volleyball, Gymnastics, Swimming, Bikes and scooters | Girls' |
| Cameras and tech | Cameras, Headphones, Tablet accessories | Girls' |
| Toys and crafts | Dolls, Arts and crafts, Games and puzzles, Books | Girls' |

Girls' is an audience lock, not a fit: every item is for girls (ADR general/0006).

**Acceptance Criteria:**
1. Given the categories endpoint, when it is called, then it returns exactly the 6 categories and 26 subcategories in the table, each with its accepted size.
2. Given a listing request with category Cameras and tech and subcategory Tutus, when it is submitted, then it is rejected with HTTP 422 and error code `CATEGORY_INVALID`.
3. Given a listing request with a category or subcategory not in the table (for example "Furniture" or "Hats"), when it is submitted, then it is rejected with HTTP 422 and error code `CATEGORY_INVALID`.

## L2-012: Size fixed by category
**Traces to:** L1-003

The listing form shall not offer a size choice. Once the seller picks a category, the form shall show the accepted size for that category as fixed, read-only text.

**Acceptance Criteria:**
1. Given a seller on the listing form, when they choose the Clothing category, then the form shows "Size: Girls'" as read-only text and no size input exists.
2. Given a seller on the listing form, when they choose Shoes, Dance, Sports, Cameras and tech or Toys and crafts, then the form shows "Size: Girls'" as read-only text.
3. Given a seller changes the category from Clothing to Cameras and tech, when the form updates, then the shown size stays "Girls'" and no size input appears.

---

## L2-013: Backend size enforcement
**Traces to:** L1-003

The API shall be the source of truth for the size rule. It shall reject any listing create or update request whose size does not match the accepted size for its category, whatever the client sends. The stored size shall always be set by the server from the category.

**Acceptance Criteria:**
1. Given a direct API request to create a Clothing listing with size "Boys' 8", when it is submitted, then the API returns HTTP 422 with error code `SIZE_NOT_ACCEPTED` and no listing is created.
2. Given a direct API request to create a Shoes listing with size "Adult S" or "Adult M", when it is submitted, then the API returns HTTP 422 with error code `SIZE_NOT_ACCEPTED`.
3. Given a direct API request to create a Cameras and tech listing with no size field, when it is submitted, then the listing is created with size "Girls'".
4. Given an active Clothing listing, when an update request changes its category to Dance, then the stored size is "Girls'".
5. Given any listing in the database, when it is read, then its size is "Girls'", whatever its category.

## L2-015: Listing fields
**Traces to:** L1-004

A listing shall have a title (5 to 80 characters), a description (20 to 2,000 characters), a category and subcategory (L2-011), a brand (1 to 50 characters, chosen from a suggested list or typed freely), a condition (L2-016), 1 to 8 photos (L2-017), a price and a shipping cost (L2-018). All text shall be trimmed and stored as plain text.

**Acceptance Criteria:**
1. Given a seller fills every required field within its limits, when they publish, then the listing is created with status Active.
2. Given a title of 4 characters or 81 characters, when the seller publishes, then publishing is refused with a title length error.
3. Given a description of 19 characters or 2,001 characters, when the seller publishes, then publishing is refused with a description length error.
4. Given a seller types a brand that is not in the suggested list, when they publish, then the listing is saved with that brand.
5. Given a title containing `<script>alert(1)</script>`, when the listing is viewed, then the text is shown literally and no script runs.
6. Given any required field is empty, when the seller publishes, then publishing is refused and every missing field is identified.

## L2-016: Item condition
**Traces to:** L1-004

The seller shall choose one condition: New with tags, New without tags, Used - Excellent, Used - Good, or Used - Fair. A Used - Fair listing shall include a description of its flaws of at least 10 characters.

**Acceptance Criteria:**
1. Given the listing form, when the seller opens the condition control, then exactly the 5 conditions are offered.
2. Given condition Used - Fair and an empty flaws field, when the seller publishes, then publishing is refused with "Describe the item's flaws".
3. Given condition Used - Fair and a flaws description of 10 or more characters, when the seller publishes, then the listing is published and the flaws are shown on the listing detail page.
4. Given a direct API request with a condition outside the 5 values, when it is submitted, then the API returns HTTP 422.

## L2-017: Listing photos
**Traces to:** L1-004

A listing shall have 1 to 8 photos. Each photo shall be JPEG, PNG or WebP, at most 10 MB, and at least 800 pixels on its shortest side. The file type shall be checked from the file's content, not its name. The server shall strip all metadata (including GPS location), re-encode the image and produce thumbnail (400px), medium (800px) and large (1600px) versions. The first photo is the cover and the seller can reorder photos.

**Acceptance Criteria:**
1. Given a seller uploads a 5 MB JPEG of 1200x1600 pixels, when the upload completes, then the photo is accepted and three resized versions are available.
2. Given a seller uploads an 11 MB image, when the upload is submitted, then it is rejected with "Photos must be 10 MB or smaller".
3. Given a seller uploads a 600x900 pixel image, when the upload is submitted, then it is rejected with a minimum size error.
4. Given a file named `photo.jpg` that is not an image, when it is uploaded, then it is rejected with HTTP 415.
5. Given a JPEG containing EXIF GPS coordinates, when it is processed, then none of the stored versions contain EXIF, XMP or GPS metadata.
6. Given a listing with 8 photos, when the seller tries to add a ninth, then the upload control is disabled and the API rejects the request.
7. Given a listing with 3 photos, when the seller drags the third photo to the first position and saves, then that photo becomes the cover in the catalog.
8. Given a listing with no photos, when the seller publishes, then publishing is refused with "Add at least one photo".

## L2-018: Price and shipping cost
**Traces to:** L1-004

The item price shall be between $1.00 and $5,000.00 inclusive, with at most two decimal places. The seller shall set a flat shipping cost between $0.00 and $100.00 inclusive. TuTuMuch shall operate in the United States only, in US dollars.

**Acceptance Criteria:**
1. Given a price of $1.00 or $5,000.00, when the seller publishes, then the price is accepted.
2. Given a price of $0.99, $5,000.01 or $10.005, when the seller publishes, then publishing is refused with a price error.
3. Given a shipping cost of $0.00, when the listing is viewed, then shipping is shown as "Free shipping".
4. Given a shipping cost of $100.01 or a negative value, when the seller publishes, then publishing is refused with a shipping cost error.
5. Given any stored price, when it is read, then it is held as an exact decimal amount and not as a floating-point number.

## L2-019: Drafts and listing status
**Traces to:** L1-004

A listing shall have one of these statuses: Draft, Active, Reserved, Sold or Removed. A seller shall be able to save an incomplete listing as a Draft and publish it later. Only Active and Reserved listings appear in the catalog. Validation rules L2-015 to L2-018 apply when publishing; drafts only need a category, and any field a draft does contain must be within its limits.

**Acceptance Criteria:**
1. Given a seller has filled in only the category and title, when they choose "Save draft", then the listing is saved with status Draft and does not appear in the catalog.
2. Given a Draft listing, when the seller completes it and publishes, then its status becomes Active and it appears in the catalog within 5 seconds.
3. Given a Draft listing, when anyone other than its seller requests it, then the API returns HTTP 404.
4. Given a Draft listing not edited for 90 days, when the clean-up job runs, then the draft and its photos are deleted and the seller was emailed 7 days before.
5. Given a seller saves a draft with a price of $0.99, when it is saved, then it is refused with the price error and nothing is stored.

## L2-020: Edit and withdraw listings
**Traces to:** L1-004

A seller shall be able to edit or withdraw an Active listing. A Reserved or Sold listing shall not be editable or withdrawable. A withdrawn listing shall become Removed and leave the catalog.

**Acceptance Criteria:**
1. Given an Active listing, when the seller changes the price and saves, then the new price is shown in the catalog and on the detail page.
2. Given a Reserved listing, when the seller tries to edit it, then the edit is refused with "This item is in someone's checkout".
3. Given a Sold listing, when the seller sends an update request, then the API returns HTTP 409 and the listing is unchanged.
4. Given an Active listing, when the seller withdraws it and confirms, then its status becomes Removed and it no longer appears in search results.
5. Given a seller who opened the edit form of an Active listing, when the listing changed after that and they save, then the save is refused with HTTP 412 `LISTING_CHANGED`, nothing is overwritten and the form offers to reload the latest version.
6. Given a withdrawn listing, when the seller tries to edit or relist it, then the API returns HTTP 409 and the listing stays Removed.

## L2-021: My listings
**Traces to:** L1-004

A seller shall have a "My listings" page showing all of their listings with cover photo, title, price, status and date, filterable by status and sorted newest first.

**Acceptance Criteria:**
1. Given a seller with 2 Draft, 3 Active and 1 Sold listing, when they open "My listings", then all 6 are shown, newest first.
2. Given the "My listings" page, when the seller filters by Sold, then only the Sold listing is shown.
3. Given a seller with no listings, when they open "My listings", then an empty state with a "Sell an item" action is shown.
4. Given the "My listings" page filtered by Sold, when the seller reloads it, then the Sold filter is still applied and each status chip still shows its count.
5. Given a seller with a Draft, a Sold and an Active listing, when they open each from "My listings", then the Draft opens in the sell form, the Sold one on its sale and the Active one on its detail page.

## L2-022: Catalog
**Traces to:** L1-005

The catalog shall show Active and Reserved listings only, as cards with cover photo, title, brand, size, condition and price, sorted newest first by default and paged 24 at a time. Reserved listings shall be marked "Reserved". Anonymous visitors shall be able to browse the catalog. Each category has its own page, titled "{Category} · TuTuMuch", at `/clothing`, `/shoes`, `/dance`, `/sports`, `/cameras-and-tech` and `/toys-and-crafts`.

**Acceptance Criteria:**
1. Given 30 Active listings, when an anonymous visitor opens the catalog, then the first 24 are shown, newest first, with a way to load the next page.
2. Given Draft, Sold and Removed listings exist, when the catalog is shown, then none of them appear.
3. Given a Reserved listing, when the catalog is shown, then its card carries a "Reserved" label.
4. Given no Active listings, when the catalog is opened, then an empty state is shown.
5. Given a listings page request with a page size above 48, when it is sent to the API, then the API caps the page size at 48.
6. Given a listings page request with a page or page size below 1, when it is sent to the API, then the API answers 400 with code `VALIDATION_FAILED`.
7. Given 24 cards are shown, when loading the next page fails, then the 24 cards stay and the visitor can try again.
8. Given Active listings in Cameras and tech, when a visitor opens `/cameras-and-tech`, then only that category's listings are shown, each card tagged "Girls".

## L2-023: Keyword search
**Traces to:** L1-005

Visitors shall be able to search by keyword. Search shall match title, brand and description, ignore case, and rank title and brand matches above description matches.

**Acceptance Criteria:**
1. Given an Active listing titled "Instax mini camera", when a visitor searches "instax camera", then that listing is in the results.
2. Given an Active listing with brand "Hanna Andersson", when a visitor searches "HANNA ANDERSSON", then that listing is in the results.
3. Given listing A has "tutu" in its title and listing B has "tutu" only in its description, when a visitor searches "tutu", then A is ranked above B.
4. Given a search that matches nothing, when results are shown, then a "No items match" state is shown with an option to clear the search and filters.
5. Given a search term longer than 100 characters, when it is submitted, then it is truncated to 100 characters before searching.

## L2-024: Filters and sorting
**Traces to:** L1-005

Visitors shall be able to filter by category, subcategory, brand (multiple), condition (multiple) and price range, and sort by newest, price low to high, or price high to low. Filters combine with each other and with the keyword using AND. Filters and sort shall be held in the page URL so a result set can be bookmarked and shared.

**Acceptance Criteria:**
1. Given filters Category = Dance and Condition = New with tags, when they are applied, then only new-with-tags dance listings are shown.
2. Given a price range of $20 to $50, when it is applied, then only listings priced from $20.00 to $50.00 inclusive are shown.
3. Given a minimum price greater than the maximum price, when the visitor applies it, then the filter is refused with a validation message.
4. Given sort "Price: low to high", when results are shown, then they are in ascending price order.
5. Given a filtered, sorted results page, when its URL is opened in a new browser, then the same filters, sort and results are shown.
6. Given brands "Carter's" and "Mini Boden" are both selected, when filters are applied, then listings of either brand are shown.
7. Given Category = Sports and Subcategory = Bikes and scooters, when the URL is opened, then it carries `category=sports&subcategory=bikes-and-scooters` and only bikes and scooters are shown.

## L2-025: Listing detail page
**Traces to:** L1-006

The listing detail page shall show a photo gallery, title, price, shipping cost, total, size, category, brand, condition (with flaws when Used - Fair), description, date listed, and the seller's display name, rating, number of completed sales and a link to their profile. Each listing shall have a stable, shareable URL.

**Acceptance Criteria:**
1. Given an Active listing, when anyone opens its URL, then every field above is shown and a "Buy now" action is visible.
2. Given a Sold listing, when its URL is opened, then it is shown with a "Sold" label and no "Buy now" action.
3. Given a Removed or Draft listing, when anyone other than its seller opens its URL, then a "This item isn't available" page is shown and the API answers HTTP 404 with the same body as for a reference that does not exist.
4. Given a listing with 5 photos, when the visitor selects a thumbnail, then that photo is shown in the main gallery view.
5. Given a seller with no completed sales, when their listing is opened, then the seller area shows "New seller" instead of a rating.

## L2-026: Buyer restrictions on a listing
**Traces to:** L1-006

A member shall not be able to buy their own listing. An anonymous visitor who chooses "Buy now" shall be sent to sign in and then returned to the listing.

**Acceptance Criteria:**
1. Given a seller viewing their own Active listing, when the page loads, then "Edit" and "Withdraw" actions are shown instead of "Buy now".
2. Given a seller sends a direct checkout request for their own listing, when it is submitted, then the API returns HTTP 422 and no order is created.
3. Given an anonymous visitor, when they choose "Buy now", then they are sent to sign in and, after signing in, returned to the same listing.

## L2-027: Checkout
**Traces to:** L1-007

A verified member shall be able to buy one Active listing at a time. Checkout shall collect a US shipping address and show the item price, shipping cost, sales tax where it applies, and the total before payment.

**Acceptance Criteria:**
1. Given a verified member chooses "Buy now" on an Active listing, when checkout opens, then it shows the item, price, shipping, tax and total, and asks for a shipping address.
2. Given a shipping address outside the United States, when the buyer continues, then checkout is refused with "TuTuMuch ships within the United States only".
3. Given a shipping address with a missing street, city, state or ZIP code, when the buyer continues, then the missing fields are identified.
4. Given a buyer has saved an address before, when checkout opens, then the saved address is offered by default.
5. Given the totals shown, when the order is placed, then the amount charged equals the total shown to the cent.
6. Given the buyer changes the shipping address and the sales tax changes, when they choose Pay, then the new total is shown and no payment is taken until they choose Pay again.

## L2-028: Listing reservation
**Traces to:** L1-007

When a buyer starts checkout, the listing shall become Reserved for that buyer for 10 minutes. While Reserved, no other member shall be able to start checkout for it. If payment does not succeed within 10 minutes, the listing shall return to Active.

**Acceptance Criteria:**
1. Given an Active listing, when buyer A starts checkout, then its status becomes Reserved and buyer B sees "Reserved" with no "Buy now" action.
2. Given a listing Reserved by buyer A, when buyer B sends a direct checkout request, then the API returns HTTP 409.
3. Given a listing Reserved 10 minutes ago without a successful payment, when the reservation expires, then the listing returns to Active.
4. Given buyer A leaves checkout, when they choose "Cancel", then the reservation is released immediately.

---

## L2-029: Each item sold once
**Traces to:** L1-007

Concurrent purchase attempts for the same listing shall result in exactly one order. This shall be guaranteed by the database (for example by optimistic concurrency on the listing), not by the client.

**Acceptance Criteria:**
1. Given an Active listing, when 50 checkout requests from different buyers arrive at the same time, then exactly one reservation succeeds and the other 49 receive HTTP 409.
2. Given an order already exists for a listing, when another payment confirmation for that listing arrives, then the second payment is refunded automatically and no second order is created.

---

## L2-030: Payment processing
**Traces to:** L1-007

Payment shall be taken through a PCI DSS compliant third-party payment provider using the provider's hosted fields or hosted page. Card numbers and security codes shall never pass through or be stored on TuTuMuch servers. TuTuMuch shall store only the provider's payment reference, card brand and last four digits. Payment results shall be confirmed from the provider's signed webhook, not from the browser.

**Acceptance Criteria:**
1. Given a buyer enters card details, when the network traffic to TuTuMuch servers is inspected, then no card number or security code is present.
2. Given a successful payment, when the provider's signed webhook is received, then an order is created with status Paid and the listing becomes Sold.
3. Given a declined payment, when the result is returned, then no order is created, the buyer sees the decline reason and can try again while the reservation lasts.
4. Given a webhook with an invalid signature, when it is received, then it is rejected with HTTP 400, logged as a security event, and no order changes.
5. Given the same webhook event is delivered twice, when the second copy is processed, then nothing changes.

## L2-031: Seller payouts
**Traces to:** L1-007

Before their first sale is paid out, a seller shall complete payout onboarding with the payment provider. The sale amount less the TuTuMuch fee shall be released to the seller when the order is Completed. The fee percentage shall be configurable and shown to the seller before they publish a listing.

**Acceptance Criteria:**

2. Given a fee of 10% and a sale of $80.00 with $10.00 shipping, when the order completes, then the seller payout is $81.00 (item and shipping less $9.00) and the fee is recorded against the order.
3. Given an order with status Paid, Shipped or Delivered, when the payout job runs, then no payout is released for that order.
4. Given the listing form, when the seller enters a price, then the form shows their estimated earnings after the fee.
5. Given a Completed order of a seller who has completed onboarding, when the payout job runs more than once, then the seller is paid once for that order, with the payout's ID as the provider's idempotency key.
6. Given a seller who returns from the payment provider's onboarding, when the provider has not reported the account as complete, then onboarding is not complete and payouts stay held; only the provider's signed notification completes it.

## L2-032: Order statuses
**Traces to:** L1-008

An order shall move through the statuses Paid, Shipped, Delivered and Completed, or end as Cancelled or Refunded. Only the transitions in this requirement shall be allowed, and every transition shall be recorded with its time and the actor.

| From | To | Triggered by |
| --- | --- | --- |
| Paid | Shipped | Seller adds tracking |
| Paid | Cancelled | Seller cancels, or ship deadline passes |
| Shipped | Delivered | Carrier reports delivery, or buyer confirms receipt |
| Delivered | Completed | Buyer confirms receipt, or 3 days pass with no open problem |
| Shipped, Delivered | Refunded | Administrator resolves a problem in the buyer's favour |

**Acceptance Criteria:**
1. Given a Paid order, when the seller tries to mark it Completed directly, then the API returns HTTP 409.
2. Given any order, when it changes status, then the history shows the old status, new status, time and actor.
3. Given a Cancelled order, when any transition is requested, then the API returns HTTP 409.

## L2-033: Shipping
**Traces to:** L1-008

**Acceptance Criteria:**
1. Given a Paid order, when the seller enters carrier "USPS" and a tracking number, then the order becomes Shipped and the buyer is emailed the tracking link.
2. Given a Paid order with no tracking after 5 business days, when the deadline job runs, then the order becomes Cancelled, the buyer is refunded in full, and the seller is notified.
3. Given a Paid order with no tracking after 3 business days, when the reminder job runs, then the seller is sent a reminder.
4. Given a Shipped order, when the carrier reports delivery, then the order becomes Delivered.
5. Given an empty or malformed tracking number, when the seller submits it, then it is refused with a validation error.

## L2-034: Completing an order

## L2-035: Cancellation before shipping
**Traces to:** L1-008

## L2-036: Problems with an order

3. Given an open problem, when an administrator resolves it with a full refund, then the order becomes Refunded, the buyer is refunded and no payout is made.
4. Given an open problem, when an administrator resolves it in the seller's favour, then the order becomes Completed and the payout is released.
5. Given an open problem, when the seller responds, then the response is visible to the buyer and administrators.
6. Given an open problem on a Delivered order, when 3 days pass after delivery, then the order is not completed automatically and the buyer cannot confirm receipt until an administrator decides.

## L2-096: Pages follow the page guidelines
**Traces to:** L1-022, L1-017, L1-016

Every routed page, dialog and notification shall follow `docs/page-guidelines.md` as mapped onto this stack by [ADR general/0009](../adr/general/0009-page-guidelines-on-the-angular-and-giddy-stack.md). Colour, type, shape and motion come only from `docs/design-system/tokens/tokens.css`. This requirement does not change the size rule (`L2-011` to `L2-013`), the conditions (`L2-016`), the catalog card contents (`L2-022`), the responsive filters (`L2-062`), cookie consent (`L2-056`), the marketing wording (`L2-078`), the launch phases (`L2-093`, `L2-094`) or accessibility (`L2-064`, `L2-065`); it adds the brand and page rules on top of them.

**Acceptance Criteria:**
1. Given any routed page, when it is rendered, then it has exactly one `h1` and exactly one TuTuMuch logo link (`tl-logo`, or `tl-mark` under 640px), and the header shows the gingham wordmark at 640px and wider and the mark below.
2. Given any page, mock or design-system page, when its styles and markup are inspected, then every colour comes from a token, no element has an inline style with a hex colour or a gradient, and no decorative blob, glow or shape is drawn; the only patterns are the polka dot and gingham inside the logo and mark.
3. Given any page, when its text is rendered, then headings and prices use Fraunces, every other text uses DM Sans, and Titan One appears only inside the logo and mark.
4. Given any view, when its buttons are counted, then at most one is a primary button (`tlButton="primary"`).
5. Given any label, heading or button, when it is read, then it is in sentence case, buttons start with a verb, there is no emoji, no exclamation point in a label, no "AI", "curated" or "elevate", at most one exclamation point on the page and only in Tilly's voice, and the catalog is called "the closet" in calls to action.
6. Given a listing grid, when it is shown, then each card shows the photo (4:5, white well), the title on one line, the brand, "Girls' · {condition}" and the price, the price rows of a row line up, and the grid has 4 columns at 992px and wider, 3 from 768px and 2 below (`L2-061`).
7. Given a listing's condition is shown as a badge, when it is rendered, then New with tags is raspberry with white text, New without tags and Used - Excellent are sunny with ink text, Used - Good is blush with ink text and Used - Fair is white with ink text and a thin ink ring.
8. Given the catalog filters, when they are shown in the sidebar or the panel (`L2-062`), then Category (when shown), Size and Condition come first and open, and Brand and Price sit behind "More filters"; a selected chip is lilac at 15% with ink text and a lilac ring.
9. Given a page is loading, when it renders, then blush skeleton blocks shaped like the content are shown and no spinner; a spinner appears only inside a busy control.
10. Given a page or list with nothing to show, when its empty state renders, then it shows Tilly's "Hello, friend" pose (unless the page already shows Tilly), one short line and one action.
11. Given a request fails, when the error state renders, then it says in plain language what happened and what to do, with a raspberry icon, and the screen is not filled with red.
12. Given a sold listing is shown, when it renders, then its photo is greyed, it carries a "Sold" badge and offers "Find similar"; given an action succeeds, then a short toast confirms it.
13. Given any screen, when Tilly images are counted, then there is at most one, in an approved pose (twirl, dance, soccer, volleyball, gymnastics, show and tell, hello, or the framed swimming tile), with alt text that starts with "Tilly" and names what she is doing.
14. Given the visitor's system requests reduced motion, when a transition would play, then it does not; otherwise transitions last 150 to 250ms with `cubic-bezier(0.23, 1, 0.32, 1)` and never animate `all`.
15. Given any icon-only button or link, when it is inspected, then it has an `aria-label`; given any `img`, then it has an `alt` attribute (empty only when decorative); given any form field, then it has a visible label.
16. Given any text and its background in light and dark themes, when `check_contrast.py` runs on the tokens, then every pair meets WCAG 2.2 AA (`L2-064`).
