Theming

Light (cream and raspberry) and dark (a plum night with a lighter raspberry) from one token file, following the device unless the member picks one.

WCAG 2.2 AAStatus: stablePage guidelines

Overview

Light is :root. Dark is [data-theme="dark"] and the same block inside @media (prefers-color-scheme: dark) for :root:not([data-theme="light"]). Each sets color-scheme so native controls match. The page guidelines define light only; ADR general/0009 keeps the dark theme as a plum night, with every pair checked by check_contrast.py.

Token tiers

TierExampleChanged by
Primitive--palette-raspberry-600Brand changes only; the only place a hex value appears
Semantic--color-accent, --radius-cardThemes
Component--btn-bg, --btn-ringComponent variants (always alias a semantic token)

Adding a theme

[data-theme="recital"] {
  --color-accent: var(--palette-raspberry-700);
  --color-bg-canvas: var(--palette-raspberry-50);
}
  • Override semantic tokens only; never add a gradient or a hex value outside the primitives.
  • Add the theme to the contrast-pairs.json runs and fix every failure.
  • Re-export tokens.json.

TuTuMuch layout tokens

The block at the end of tokens.css aliases the 12L names (ink, paper and signal ramps, --color-brand) onto the palette. A theme never overrides them directly; it overrides the semantic tokens they point to. See Color.

tokens.json

tokens/tokens.json is a DTCG export ($type, $value, aliases as {group.token}, dark overrides under $extensions). Generate it with tokens_to_json.py; never edit it by hand.

Do and don’t

  • Do test both themes for every new component.
  • Don’t invert light values for dark; design dark from roles.
  • Don’t reference primitives from components.
  • Don’t recolour the logo, the mark or Tilly per theme; they stay the same.
